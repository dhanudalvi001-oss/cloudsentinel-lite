# CloudSentinel-Lite

Detects risky S3 public-access changes on buckets in scope and automatically re-enables **S3 Block Public Access**, then emails an alert.

## How it works

```
S3 API call (e.g. DeleteBucketPublicAccessBlock)
  -> CloudTrail (management events)
  -> EventBridge rule (default bus)
  -> Lambda: cloudsentinel-remediator
  -> enables Block Public Access + publishes SNS email
```

Monitored events: `PutBucketAcl`, `PutBucketPolicy`, `DeleteBucketPublicAccessBlock`, `PutBucketPublicAccessBlock`.

The Lambda only acts on buckets whose name starts with `ScopePrefix` (default `cs-demo-`). Its IAM role is limited to the same prefix.

## IMPORTANT: a CloudTrail trail is required

EventBridge only receives `AWS API Call via CloudTrail` events when a CloudTrail trail is enabled in the account. CloudTrail **Event history** (what `aws cloudtrail lookup-events` shows) does not feed EventBridge. Without a trail the rule never fires, with no error anywhere.

`template.yaml` creates the trail for you: a log bucket (Block Public Access on, logs expire after 3 days), a bucket policy for CloudTrail, and a single-region management-events trail. Do not remove it.

## Parameters

| Parameter | Default | Meaning |
|---|---|---|
| `AlertEmail` | (required) | Address that receives SNS alerts. Confirm the subscription email or you will get no alerts. |
| `DryRun` | `true` | `true` = alert only, change nothing. `false` = also enable Block Public Access. |
| `ScopePrefix` | `cs-demo-` | Only buckets with this name prefix are handled. |

Always pass `DryRun` explicitly when redeploying. The template default is `true`, so omitting it silently switches a live setup back to dry-run.

## Deploy (plain CloudFormation, no SAM CLI needed)

```powershell
$ACCOUNT = aws sts get-caller-identity --query Account --output text
$PKG_BUCKET = "cs-pkg-$ACCOUNT"
aws s3api create-bucket --bucket $PKG_BUCKET --region us-east-1
aws s3api put-public-access-block --bucket $PKG_BUCKET --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

aws cloudformation package --template-file template.yaml --s3-bucket $PKG_BUCKET --output-template-file packaged.yaml

aws cloudformation deploy --template-file packaged.yaml --stack-name cloudsentinel --capabilities CAPABILITY_IAM CAPABILITY_AUTO_EXPAND --parameter-overrides DryRun=false AlertEmail=you@example.com ScopePrefix=cs-demo-
```

`packaged.yaml` is generated by the package step. Edit `template.yaml`, never `packaged.yaml`.

After the first deploy, confirm the SNS subscription email, then wait about 5 minutes before testing (a new trail needs a few minutes before events reach EventBridge).

## Test it end to end

```powershell
$B = "cs-demo-$ACCOUNT-1"
aws s3api create-bucket --bucket $B --region us-east-1
aws s3api delete-public-access-block --bucket $B
Start-Sleep -Seconds 180
aws s3api get-public-access-block --bucket $B
aws logs filter-log-events --log-group-name /aws/lambda/cloudsentinel-remediator --start-time ([DateTimeOffset]::UtcNow.AddMinutes(-10).ToUnixTimeMilliseconds()) --query "events[].message" --output text
```

Expected: all four settings `true`, and a log entry `FIXED: Block Public Access enabled` with `Done by:` showing your IAM user. A second `Already protected` entry is the Lambda reacting to its own change and stopping, so there is no loop.

You can also test the handler directly, skipping CloudTrail:

```powershell
'{"detail":{"eventName":"PutBucketAcl","requestParameters":{"bucketName":"cs-demo-test"},"userIdentity":{"arn":"manual-test"}}}' | Set-Content -Path event.json -Encoding ascii
aws lambda invoke --function-name cloudsentinel-remediator --payload fileb://event.json out.json
```

## Limitations

- The handler acts on the event name alone. Any monitored event on an unprotected in-scope bucket gets the full block, whether or not the change made the bucket public.
- It enables Block Public Access but does not remove the offending ACL or bucket policy. Those stay attached and are only neutralised by the block.
- Single region (us-east-1). The rule, Lambda and trail all live there.
- Buckets outside `ScopePrefix` are ignored.

## Troubleshooting

If a real change is not remediated:

1. `aws cloudtrail describe-trails` must list a trail, and `get-trail-status` must show `IsLogging` true.
2. Check the rule's `TriggeredRules` metric. No metric means events are not reaching the rule.
3. Check the Lambda log group `/aws/lambda/cloudsentinel-remediator`. An empty log with a deleted trail is the classic signature of the missing-trail problem above.
4. Check `DRY_RUN` on the function. `true` means it alerts but does not fix.
5. Wait a few minutes. Delivery right after creating a trail can lag.

Shell tip for PowerShell: variables such as `$B` do not survive a new terminal. If `--bucket` errors with "expected one argument", the variable is empty.

## Teardown

The trail log bucket must be empty before the stack can be deleted.

```powershell
$TB = aws cloudformation describe-stack-resource --stack-name cloudsentinel --logical-resource-id TrailLogBucket --query "StackResourceDetail.PhysicalResourceId" --output text
aws s3 rm s3://$TB --recursive
aws cloudformation delete-stack --stack-name cloudsentinel
```

Then remove what the stack does not own: the Lambda log group (`/aws/lambda/cloudsentinel-remediator`), the packaging bucket, and any `cs-demo-*` test buckets.
